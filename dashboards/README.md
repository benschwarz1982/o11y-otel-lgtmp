## `templates/` Mirrors `instrumentation/`'s 3-Layer Model

[`instrumentation/`](../instrumentation/) organizes its templates as
schema → platform/runtime → application - `templates/` here uses the
same three directory names, one dashboard shape per platform/
middleware/application type:

- **`templates/platforms/`** - one per platform shape (Linux/Windows/
  network device/object storage/the AKS cluster itself).
- **`templates/middleware/`** - one per middleware/runtime shape
  (currently just PostgreSQL, unused live).
- **`templates/applications/`** - one per application shape. Still
  reusable templates keyed by *telemetry shape*, not one folder per
  real system the way `instrumentation/applications/<id>-<name>/` is -
  `k8s-app.template.json` lives here too as the generic Kubernetes-pod
  default (its shape is unambiguously application-shaped - active
  series/traces/logs by `k8s_namespace_name` - not platform-shaped,
  even though it's what any manifest gets when it doesn't specify
  one).

A manifest's `dashboard_template` field (see
[`manifests/schema.json`](../manifests/schema.json)) is the
subfolder-qualified filename, e.g. `"platforms/linux-host.template.json"`
- `scripts/generate-system-dashboard.py` joins it directly onto
`templates/`, no search/fallback logic involved.

**Deliberately not ID-prefixed, unlike `instrumentation/platforms/`'s
own folders** - `instrumentation/`'s own two layers aren't consistent
with each other on this either (`platforms/` prefixes every folder,
`middleware/` prefixes none), so "match `instrumentation/`" doesn't
resolve to one answer on its own. `templates/` here follows
`middleware/`'s convention: every file here is a genuinely reusable
*shape*, not one system's own copy, and IDs would actively mislead in
two ways `instrumentation/platforms/` doesn't have to deal with -
`k8s-app.template.json`/`postgresql.template.json` have no live system
to derive an ID from at all, and prefixing e.g.
`applications/tomcat-vm.template.json` with `4711-` would collide
almost identically with the *generated* `4711-mitarbeiterverzeichnis.json`
this template produces - two different things (shape catalog vs. real
output) that `instrumentation/` never has to distinguish, since it
never pre-generates a separate static artifact the way dashboards
does.

## Why `shared/` and the Flat Per-System Files Sit Outside That Model

They're generated/curated **output** - real dashboards, not
templates - not one of the three layers above:

- **`shared/`** - dashboards that aren't tied to any one tenant at all
  (cross-tenant operator view, collector self-monitoring). Same
  "doesn't fit the layering" reasoning
  [`collector-gateway/README.md`](../collector-gateway/README.md)
  already documents for the gateway.
- **`<system_id>-<slug>.json`, directly under `dashboards/`** - one
  dashboard per onboarded system (not per environment - an in-dashboard
  `env` variable switches between whichever environments that system
  is actually onboarded into, see the main README's
  [B8](../docs/setup.md#b8-per-system-dashboards-onboarding)),
  machine-generated by
  [`scripts/generate-system-dashboard.py`](../scripts/generate-system-dashboard.py)
  (invoked by `scripts/provision.py` on every onboarding merge) and
  committed to git once it happens. Both platform-type and
  application-type systems land here side by side - e.g. 1286 Linux
  Basis and 4721 Kundenverwaltung each get their own flat file - so
  this can't nest under `templates/applications/` without misdescribing
  every platform's own dashboard. Used to be one file per system *per
  environment*, split into `prod/`/`at`/`eng` subdirectories - collapsed
  to one flat file per system after finding live that Grafana's
  dashboard file-provisioner only reliably supports one folder level
  from its mount root (a confirmed, open upstream limitation,
  [grafana/grafana#107158](https://github.com/grafana/grafana/issues/107158)),
  which broke a `<env>/<system_id>` nested Grafana folder scheme an
  earlier version of this repo tried.

## Why This Isn't Under `k8s/`

It used to be (`kubernetes/dashboards/`).
[`k8s/`](../k8s/) is organized by deployment mechanism -
everything there is applied as a Kubernetes object. Dashboards are
still *applied* that way (as ConfigMaps, watched by Grafana's sidecar -
see `helm/values/grafana-values.yaml`), but the template catalog and
generated output themselves are content this repo authors and reasons
about on their own terms, not "Kubernetes platform" content - same
reasoning that moved the gateway collector out to
[`collector-gateway/`](../collector-gateway/).
